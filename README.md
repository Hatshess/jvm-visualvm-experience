Heap 

- Размер (Size) ~1 ГБ (1 048 576 000 B), из них используется около 615 МБ (645 677 272 B).
- Видно резкое увеличение размера кучи в момент создания объектов (примерно 13:41:05 - 13:41:20).
- Используемая память растёт пропорционально созданию 3 × 5 000 000 объектов, что логично.
- Резервируемый размер кучи растёт, чтобы вместить новые объекты, что нормально для JVM, т.к. он динамично расширяется под нагрузку.


![Скриншот 15-11-2025 134300](https://github.com/user-attachments/assets/213e9d26-1ff6-4794-8ac8-1c375642748a)


Metaspace

- Размер около 26 МБ (26 476 544 B), используется практически весь выделенный размер (26 106 504 B).
- Размер Metaspace не меняется после начального скачка, что говорит о том, что все необходимые классы загружены, загрузка классов закончилась в начале (соответствует логу с загрузкой 6431 класса).
- Не наблюдается скачков или утечек — размер стабилен.

![Скриншот 15-11-2025 134309](https://github.com/user-attachments/assets/5ea2c747-30b9-4fc8-864b-1338f76d05d7)


Classes 

- Загружено всего 6431 класс, из которых 1351 — shared loaded (разделённые).
- Ни одного выгруженного класса (Total unloaded = 0), что типично при отсутствии динамической подгрузки/выгрузки классов в текущем запуске.
- Рост количества классов происходит в начале (согласно графику), что совпадает с логом загрузки Spring, Netty, Vertx.

Вывод

- JVM динамически подстраивается под нагрузку: куча увеличивается по мере создания объектов, а Metaspace стабилен.
- Нет признаков утечки памяти или аномалий в загрузке классов.
- Загрузка классов и создание объектов проходят нормально, использование памяти выглядит адекватным для такой нагрузки (15 миллионов объектов).
- Для дальнейшего анализа можно следить за GC (сборкой мусора), временами отклика и работать с параметрами JVM, если необходимо оптимизировать производительность.

Такой мониторинг помогает оценить, как работает приложение и JVM под высокой нагрузкой.
